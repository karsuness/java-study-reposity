# 分布式锁

> 来源：`分布式锁.md`

分布式锁主流的实现有关系型数据库、缓存（Redis、Memcached）、Zookeeper

  * **基于数据库（MySQL）实现** ：MySQL 本身有自带的悲观锁 `for update` 关键字，也可以自己实现悲观/乐观锁来达到目的；
  * **基于缓存（Redis，Memcached等）实现** :

    * 利用 Memcached 的 `add` 命令。此命令是原子性操作，只有在 `key` 不存在的情况下，才能 `add` 成功，也就意味着线程得到了锁。
    * 和 Memcached 的方式类似，利用 Redis 的 `setnx` 命令。此命令同样是原子性操作，只有在 `key` 不存在的情况下，才能 `set` 成功。
  * **基于Zookeeper实现** ：利用 Zookeeper 的顺序临时节点，来实现分布式锁和等待队列。Zookeeper 的设计初衷是提供分布式协调服务（配置管理、命名服务、选主、分布式锁等），分布式锁只是其中一种典型用法。

分布式锁主要解决的是多个客户端对共享资源进行操作出现数据不一致的情况

从性能方面考虑缓存的性能最高、从可靠性来说Zookeeper最具有优势

## Redis

使用Redis实现分布式锁主要依赖setnx（不存在则插入否则失败）来实现加锁。del命令来实现解锁。通过expire设置超时时间来防止在线程获得锁的过程中挂掉未显式删除key的情况，Redis仍然存在3个问题。

1.setnx和expire的非原子性

当线程获取到锁之后，没有设置过期时间，在运行过程中还没有及时将key删除就会造成死锁，别的线程就无法获得锁，解决这个问题的方法是使用set命令

```java
set（key，1，30，NX）
```

2.del导致误删

假设一个线程A获得锁并且设置超时时间为30秒，但是这个线程运行的很慢，超过30秒还没有运行结束，这时候锁过期自动释放，另一个线程B获得锁。随着原来线程A执行完任务，开始执行del命令来释放锁，但是线程B还没有执行完，线程A实际上删除的是线程B的锁。为了避免这种情况可以在加锁的时候把一个唯一标识（如UUID，分布式场景下不同JVM的线程ID可能重复，不建议直接用线程ID）设置为value，并在删除之前验证key对应的value是不是自己的唯一标识

加锁

```java
String threadId = UUID.randomUUID().toString()
set（key，threadId ，30，NX）
```

解锁

```java
if（threadId .equals(redisClient.get(key))）{
    del(key)
}
```

3.出现并发问题

如上述问题，虽然A线程误删B线程key的问题解决了，但是同一个时间内有A、B两个线程访问代码块。为了解决这个问题可以让获得锁的线程开启一个守护线程，用来给快要过期的锁加时间。当正式线程执行完任务之后会显式关闭守护线程

## MySQL

MySQL实现分布式锁在性能上不如Redis和Zookeeper但是优点是不需要引入新的组件

MySQL实现锁主要有三个原理一个是基于唯一索引（insert）一个是基于排他锁（for update）、添加版本号的乐观锁

insert实现方式

    * 获取锁时在数据库中insert一条数据，包括id、方法名(唯一索引)、线程名(用于重入)、重入计数
    * 获取锁如果成功则返回true
    * 获取锁的动作放在while循环中，周期性尝试获取锁直到结束或者可以定义方法来限定时间内获取锁
    * 释放锁的时候，delete对应的数据

for update实现方式

    * 获取锁可以通过，在select语句后增加`for update`，数据库会在查询过程中给数据库表增加排他锁。当某条记录被加上排他锁之后，其他线程无法再在该行记录上增加排他锁，我们可以认为获得排它锁的线程即可获得分布式锁；
    * 其余实现与使用唯一索引相同；
    * 释放锁通过`connection.commit();`操作，提交事务来实现

```java
/**
 * 加锁
 */
public boolean lock() {
    // 开启事务
    connection.setAutoCommit(false);
    // 循环阻塞，等待获取锁
    while (true) {
        // 执行获取锁的sql
        result = select * from methodLock where method_name = xxx for update;
        // 结果非空，加锁成功
        if (result != null) {
            return true;
        }
    }
    // 加锁失败
    return false;
}

/**
 * 解锁
 */
public void unlock() {
    // 提交事务，解锁
    connection.commit();
}
```

一般是通过为数据库表添加一个 `version` 字段来实现读取出数据时，将此版本号一同读出.

之后更新时，对此版本号加1，在更新过程中，会对版本号进行比较，如果是一致的，没有发生改变，则会成功执行本次操作；如果版本号不一致，则会更新失败。实际就是个`CAS`过程。

## Zookeeper

  * 大家都是上来直接创建一个锁节点下的一个接一个的临时顺序节点
  * 如果自己不是第一个节点，就对自己上一个节点加监听器
  * 只要上一个节点释放锁，自己就排到前面去了，相当于是一个排队机制。

而且用临时顺序节点的另外一个用意就是，如果某个客户端创建临时顺序节点之后，不小心自己宕机了也没关系，zk感知到那个客户端宕机，会自动删除对应的临时顺序节点，相当于自动释放锁，或者是自动取消自己的排队。
